# 汎用インシデント タスク（ドラフト）

脅威の種類を問わず、すべてのインシデントへ積むことを想定したタスク案です。

出典は [Microsoft Defender ポータルでインシデント対応ワークフローを計画する](https://learn.microsoft.com/ja-jp/defender-xdr/plan-incident-response)、[Microsoft Defender でインシデントを管理する](https://learn.microsoft.com/ja-jp/defender-xdr/manage-incidents)、[Microsoft Defender ポータルでインシデントを調査する](https://learn.microsoft.com/ja-jp/defender-xdr/investigate-incidents) です。

⚠️ **Learn はインシデント対応の進め方を示すもので、タスク化を指示しているわけではありません。** 本ドラフトは、公式のタスク化 Playbook 3 本（Phishing / Ransomware / BEC）と同じ構成へ読み替えた案です。

## 設計方針

| 方針 | 内容 |
| --- | --- |
| 対象 | 脅威の種類を問わないすべてのインシデント |
| 位置づけ | 共通の骨格。該当する脅威には 3 本が上乗せされる |
| 粒度 | 6 件。Phishing の 6 件と同程度に収める |
| 文体 | 判断を促す問いかけ。作業名の羅列にしない |
| 書式 | `<dt><b>◆ 問い</b></dt>` と `<dd>◇ 補足</dd>`（3 本と同じ） |
| 判定 | Playbook 内で種別を判定しない。適用範囲はオートメーション ルールで決める |

🔴 **3 本と違い、適用対象を絞るキーワードがありません。** 全インシデントへ積む前提であれば、Logic Apps の実行回数と、タスクが増えることによる画面の見づらさを確認してください。

## タスク一覧

| # | タスク名 | 目的 |
| --- | --- | --- |
| 1 | はじめに | このチェックリストの使い方と全体の流れ |
| 2 | トリアージ | 優先度の判断、担当者の割り当て、タグ付け |
| 3 | 調査と分析 | 攻撃ストーリー、アラート、資産、証拠の確認 |
| 4 | 封じ込め | 拡大の停止と、自動対応の結果確認 |
| 5 | 回復 | 影響を受けた資産と構成の復旧 |
| 6 | 解決と文書化 | 分類、解決メモ、再発防止への反映 |

## 1. はじめに

```html
<dt><b>◆ このチェックリストは、脅威の種類を問わず共通する対応の流れを示します。</b></dt>
<dd>◇ トリアージ、調査と分析、封じ込め、回復、解決と文書化の順に進めます。</dd>
<dd>◇ 詳細は <a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/plan-incident-response">インシデント対応ワークフローの計画</a> を参照してください。</dd>
<dt><b>◆ 上から順に進めますが、判断がついた段階で前後しても構いません。</b></dt>
<dd>◇ 実施しなかったタスクは「スキップ済み」にし、理由をコメントへ残します。</dd>
<dt><b>◆ フィッシング、ランサムウェア、BEC に該当する場合は、専用のタスクが別途追加されます。</b></dt>
<dd>◇ その場合は、本チェックリストを土台として、脅威別の手順を優先します。</dd>
```

## 2. トリアージ

```html
<dt><b>◆ このインシデントは、今すぐ着手すべきものですか？</b></dt>
<dd>◇ 重大度、影響を受ける資産、<a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/incident-queue">インシデント キュー</a> の優先度評価を確認します。</dd>
<dd>◇ 重要資産のタグが付いている場合は、優先度を上げることを検討します。</dd>
<dt><b>◆ 担当者は決まっていますか？</b></dt>
<dd>◇ [インシデントの管理] から所有者を割り当てます。所有権は関連するすべてのアラートへ反映されます。</dd>
<dt><b>◆ 状態は最新ですか？</b></dt>
<dd>◇ 着手したら、状態を「進行中」へ変更します。</dd>
<dt><b>◆ 後から検索できるようにタグを付けましたか？</b></dt>
<dd>◇ 攻撃の種類や自動対応の実施状況は、システム タグとして自動で付く場合があります。</dd>
<dd>◇ 運用上の分類が必要であれば、カスタム タグを追加します。</dd>
```

## 3. 調査と分析

```html
<dt><b>◆ 攻撃の全体像を把握しましたか？</b></dt>
<dd>◇ <a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/investigate-incidents">攻撃ストーリー</a> で、範囲、重大度、検出ソース、影響を受けた資産を確認します。</dd>
<dt><b>◆ どのアラートが、どの製品から上がっていますか？</b></dt>
<dd>◇ [アラート] タブで、各アラートの発生元、範囲、重大度を確認します。</dd>
<dd>◇ 複数製品のアラートが相関している場合、攻撃が複数の領域にまたがっている可能性があります。</dd>
<dt><b>◆ 影響を受けた資産は特定できましたか？</b></dt>
<dd>◇ [資産] タブで、デバイス、ユーザー、メールボックス、アプリ、クラウド リソースを確認します。</dd>
<dd>◇ 侵害されたアカウントが、高い権限を持っていないかを確認します。</dd>
<dt><b>◆ 自動調査と対応は、すでに何を実施しましたか？</b></dt>
<dd>◇ [調査] タブで、<a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/m365d-autoir">自動調査と対応</a> の結果を確認します。</dd>
<dd>◇ 承認待ちのアクションが残っていないかを確認します。</dd>
<dt><b>◆ 証拠の判定と修復状況を確認しましたか？</b></dt>
<dd>◇ [証拠と対応] タブで、各エンティティの判定（悪意のある / 疑わしい / クリーン）を確認します。</dd>
```

## 4. 封じ込め

```html
<dt><b>◆ 攻撃の拡大を止めるために、今できることは何ですか？</b></dt>
<dd>◇ 侵害されたユーザーの無効化、影響を受けたデバイスの分離、敵対的な IP アドレスのブロックを検討します。</dd>
<dd>◇ 封じ込めは、証拠の保全と両立させます。調査に必要なログを失わないよう順序を検討します。</dd>
<dt><b>◆ 自動攻撃の中断は動作しましたか？</b></dt>
<dd>◇ <a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/automatic-attack-disruption">自動攻撃の中断</a> により、すでに封じ込めが実行されている場合があります。</dd>
<dd>◇ 実行済みの処置を把握してから、追加の対応を判断します。</dd>
<dt><b>◆ 承認待ちの修復アクションは残っていませんか？</b></dt>
<dd>◇ [証拠と対応] タブから、修復アクションを承認または拒否します。</dd>
<dt><b>◆ 影響範囲の外にも、同じ侵害が広がっていませんか？</b></dt>
<dd>◇ 必要に応じて <a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/advanced-hunting-overview">高度な追及</a> で、同様の痕跡を探します。</dd>
```

## 5. 回復

```html
<dt><b>◆ 影響を受けた資産を、インシデント前の状態へ戻せますか？</b></dt>
<dd>◇ バックアップからの復元、または以前の構成の手動復元を検討します。</dd>
<dd>◇ 復元前に、侵害の原因が解消されていることを確認します。原因が残ったままの復旧は再感染につながります。</dd>
<dt><b>◆ 封じ込めで停止した業務を再開できますか？</b></dt>
<dd>◇ 無効化したアカウント、分離したデバイス、停止したサービスを、確認のうえ段階的に戻します。</dd>
<dt><b>◆ 利用者への連絡は済んでいますか？</b></dt>
<dd>◇ アカウントのリセットや端末の隔離を行った場合は、本人と関係部門へ状況を共有します。</dd>
```

## 6. 解決と文書化

```html
<dt><b>◆ 分類は設定しましたか？</b></dt>
<dd>◇ 真陽性、情報提供・想定されるアクティビティ、誤検知のいずれかを選び、種類まで指定します。</dd>
<dd>◇ 分類は検出の精度向上に使われます。未設定のまま閉じないでください。</dd>
<dt><b>◆ 解決メモを残しましたか？</b></dt>
<dd>◇ 状態を「解決済み」にすると、解決理由を記録する欄が表示されます。</dd>
<dd>◇ 判断の根拠と実施した処置を書くと、類似インシデントの対応時に参照できます。</dd>
<dt><b>◆ 対応の経緯はコメントへ残しましたか？</b></dt>
<dd>◇ アクティビティ ログへコメントを追加すると、インシデントの履歴として残ります。</dd>
<dt><b>◆ 今回の対応から、変えるべきことはありますか？</b></dt>
<dd>◇ <a target='_blank' href="https://learn.microsoft.com/ja-jp/defender-xdr/threat-analytics">脅威分析</a> で、同種の攻撃の傾向を確認します。</dd>
<dd>◇ 検出ルール、セキュリティ構成、運用手順のうち、見直すべきものを判断します。</dd>
```

## 実装方法の選択

| 方法 | 向く場面 | 注意点 |
| --- | --- | --- |
| オートメーション ルールの `タスクの追加` | 6 件程度をそのまま積む | Playbook 不要・課金なし。HTML の表現力は Playbook より限定的 |
| Playbook | 文面を HTML で作り込む、条件分岐を入れる | Logic Apps の従量課金。3 本を雛形にできる |
| Incident Tasks REST API | 既存の手順管理基盤から投入する | 自前の実行基盤が必要 |

⭐ **まずは組み込みの `タスクの追加` で運用を試し、文面や分岐が足りなくなってから Playbook 化するのが安全です。**

## 未検証の事項

- 全インシデントへ 6 件を積んだ場合の、画面の見やすさと運用負荷
- 3 本と併用したときの表示順と重複感
- 組み込みの `タスクの追加` で、上記 HTML がどこまで再現されるか
